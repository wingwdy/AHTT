## 1. 文档目的

本文定义 AHTT V3.12 平台模块在 D3-A32FB_MCU 中的软件架构、文件职责、状态机、收发数据流、接口边界、异常恢复、资源控制和验证门禁，为后续分阶段代码方案与实现提供统一基线。

本文是软件架构设计评审稿，不替代 V3.12 原始协议，不逐字复制全部命令字段，也不表示相关代码已经实现或验证。命令级字段、长度、单位、范围、应答和时序继续由 `AHTT-V3.12-事实台账.md` 与 `AHTT-V3.12-命令追踪矩阵.md` 管理。

本文存在未关闭的 `[TBD]`、`[TBC]` 或 `[CONFLICT]` 时，不得标记为已确认、已冻结或正式发布。

## 2. 目标、范围与非目标

### 2.1 设计目标

- 在当前 `Asw_PlatM`、`FrameQueue`、`Cdd_NetM` 和充电业务架构内新增 AHTT 平台能力。
- 以 `Protocol_GN` 为强制同构模板，建立 Types、Send、Recv、M 四层协议模块。
- 固定采用 `Init → Offline → Login → Normal` 四态主状态机。
- M1沿用GN的FrameQueue解码模式，支持当前FrameQueue接收块内的粘包、连续多帧和错误帧重新同步；跨FrameQueue接收块半包暂不保证恢复。
- 建立流水号、单号幂等、应答关联、超时、重试和断线恢复机制。
- 首期按 `reference/协议点检表.xlsx` 中标记 `YES` 的 23 个协议命令以及二维码功能实现。
- `0xD1` 纳入首期，复用当前 `SS_Ucm` OTA 框架，升级调用方式参考 GN 升级处理路径。
- 保证平台命令不能绕过当前充电、安全、故障和升级条件仲裁。
- 为本地报文验证、Keil 编译、板端抓包和平台联调建立可追踪入口。

### 2.2 首期功能范围

| 类别 | 首期命令或功能 |
|---|---|
| 签到与设置 | `0x01`、`0x02`、`0x03`、`0x04`、`0x0A`、`0x0B` |
| 在线保持 | `0x81` |
| 核心充电 | `0x4D`、`0x4C`、`0x4B`、`0x93`、`0x94` |
| 运维 | `0x84`、`0x85`、`0x95`、`0x96` |
| 告警 | `0xC1`、`0xC2`、`0xC3`、`0xC4`、`0xC5`、`0xC7` |
| 升级 | `0xD1` |
| 非协议功能 | 屏幕二维码显示 |

首期协议命令总数为 23。每个命令均存在设备发送或设备接收方向及其对应应答方向，因此发送定义表和接收定义表均按 23 项设计；二维码不占协议命令表项。

### 2.3 非目标

- 不直接复制旧参考项目的单文件 AHTT 实现。
- 不实现点检表首期范围之外的其他 V3.12 命令。
- 不为 AHTT 重构所有平台的公共协议框架。
- 不改变当前 GN、YKC、XDT 等既有平台行为。
- 不在协议模块内直接操作 Flash 分区、继电器、充电全局变量或旧网络缓冲区。
- 不复制旧 AHTT 实现中的固定升级地址、账号、口令、目录或板型分支。
- 不以 Keil 编译成功代替报文、板端或平台验证。

## 4. 架构方案选择

### 4.1 采用方案：GN 同构骨架加纵向业务切片

AHTT 使用与 `Protocol_GN` 相同的文件职责、表驱动收发机制、公共收发控制项、主状态机和平台描述符接入方式；协议差异仅限帧格式、命令、参数、时序和 AHTT 特有业务状态。

后续按以下纵向切片实施：

1. 基础帧、CRC、流水号、TCP 流式解帧和平台接入。
2. `0x01` 签到与 `0x81` 心跳闭环。
3. 参数设置、查询和 NVM。
4. `0x4D → 0x93 → 0x4B → 0x94` 充电闭环及 `0x4C` 刷卡。
5. 时间、状态、告警和二维码。
6. `0xD1` 与 UCM OTA 闭环。
7. 断网、掉电、重复命令、长稳和压力验证。

### 4.2 未采用方案

| 方案 | 不采用原因 |
|---|---|
| 复制旧 AHTT 单文件后拆分 | 会把旧协议常量、全局状态、Flash、网络和业务耦合一起带入当前项目 |
| 新建独立于 `Asw_PlatM` 的平台任务和网络栈 | 重复现有平台管理、FrameQueue、网络与看门狗机制，增加并发和资源风险 |
| 先抽象所有平台的通用协议引擎 | 超出 AHTT 接入范围，可能改变既有平台行为，无法保证最小改动 |

## 5. 系统上下文与分层边界

```text
平台 Server
   │ TCP
   ▼
Cdd_NetM ── FrameQueue RX/TX
   │
   ▼
Asw_PlatM 协议描述符
   │
   ▼
Protocol_AHTT
 ├─ Recv：流式解帧、校验、解析、应答关联、超时
 ├─ Send：业务组包、公共帧封装、发送调度
 ├─ M：四态状态机、周期业务、业务仲裁
 └─ Types：命令、帧、上下文和控制表类型
   │
   ├─ Asw_ChargeIf / Asw_Monitor / 错误处理
   ├─ MS_Nvm / 订单块
   ├─ SS_Tm
   ├─ SS_Ucm
   └─ 二维码配置与显示接口
```

### 5.1 分层约束

- 网络驱动只负责连接和字节流传输，不解析 AHTT 命令。
- `FrameQueue` 只承载 TCP 字节流，不执行业务动作。
- Recv 层负责不可信输入校验和字段解析，不直接控制继电器或写 Flash 分区。
- Send 层只读取规范化业务数据并组包，不拥有订单和充电状态。
- M 层负责协议状态、周期调度、命令前置条件和当前业务接口适配。
- 参数持久化必须通过 `MS_Nvm`；OTA 必须通过 `SS_Ucm`。
- 平台远程命令不得绕过 `Asw_Monitor`、充电业务和本地故障保护。
- 设备级命令没有协议端口字段时，不得借用固定枪号表达设备级状态。

### 7.3 允许的非同构点

以下差异由 AHTT 协议语义直接导致，允许偏离 GN，但必须在代码方案中逐项核对：

- 帧头字段、长度含义、设备号、CRC字节序和命令宽度。
- 平台请求与应答可能使用相同命令字，必须由发送/接收控制项的方向和关联状态区分。
- AHTT 上、下行各自维护流水号，设备对平台请求应答时回传平台流水号。
- 16位业务单号幂等语义。
- `0x81` 状态位图、`0x93/0x94` 订单数据、AHTT告警和参数字段。
- `0xD1` 到 UCM 的协议适配。
- AHTT特有签到退避标志或子状态；不得新增平行主状态机。

## 8. 平台集成设计

### 8.1 `Asw_PlatM` 接入

必须在 `AswPlatType_Enum` 中将 `eAswPlatType_AHTT`追加到`eAswPlatType_DXL`之后、`eAswPlatType_Count`之前，并同步检查运维协议中平台编号映射。不得把AHTT插入既有枚举项之间，不得改变GN、YKC、XDT、GNP、YKC16、TT24、XJ、GWE、AP和DXL已有数值；该约束用于保护NVM中的平台类型和历史订单`protocolType`兼容性。

必须在`AswPlatCardType_Enum`中以同样的追加方式增加`eAswPlatCardType_AHTT`，并在`c_stAswPlatMCardDescriptorTable`中绑定`eCddCardType_UUID`。

`c_stAswPlatMProtocolDescriptorTable` 必须增加 AHTT 描述符：

| 描述符字段 | AHTT绑定 |
|---|---|
| `pName` | `"ahtt"` |
| `cProtoMeaning` | `"安徽铁塔"` |
| `eSocketType` | `eCddNetMSocketType_TCP` |
| `pFuncFillLinkPara` | `IotAHTT_FillLinkPara` |
| `pFuncInit` | `IotAHTT_InitMemory` |
| `pMainFunction` | `IotAHTT_MainFunction` |

## 9. 报文与字节序设计

### 9.1 固定报文头

根据用户确认的报文头结构，AHTT固定头定义为：

```c
typedef struct
{
    uint8_t head;
    uint8_t len[2];
    uint8_t ver;
    uint8_t device_num[5];
    uint8_t ser[2];
    uint8_t cmd;
} IotAHTTFrameHead_Struct;
```

| 偏移 | 长度 | 字段 | 规则 |
|---:|---:|---|---|
| 0 | 1 | `head` | 固定 `0xEA` |
| 1 | 2 | `len` | 低字节在前，表示长度字段之后的全部字节数 |
| 3 | 1 | `ver` | 固定 `0x01` |
| 4 | 5 | `device_num` | `platPileDn`转换后的5字节BCD，按字节逆序发送 |
| 9 | 2 | `ser` | 低字节在前 |
| 11 | 1 | `cmd` | 1字节命令 |
| 12 | N | 参数 | 命令相关 |
| 12+N | 2 | CRC | CRC16-MODBUS，低字节在前 |

固定头长度为 12 字节。完整帧长度和声明长度关系为：

```text
声明长度 = 1版本 + 5设备号 + 2流水号 + 1命令 + N参数 + 2CRC
         = 11 + N

完整帧长度 = 声明长度 + 3
           = 14 + N
```

设备号转换规则：

```text
platPileDn：3400300000
顺序BCD：  34 00 30 00 00
线上字节： 00 00 30 00 34
```

`platPileDn`必须是10位十进制数字。初始化时使用公共BCD转换能力生成5字节顺序BCD，再按字节逆序保存到AHTT上下文。配置为空、长度不是10或包含非数字字符时，不得发送签到或其他业务报文，并保持平台离线故障。

### 9.2 帧级架构要求

| 要求编号 | 架构要求 |
|---|---|
| AHTT-PROTO-001 | 接收端必须在访问固定头前确认缓冲区至少包含12字节。 |
| AHTT-PROTO-002 | 接收端必须按`声明长度 + 3`计算完整帧长度，并在读取CRC或参数前确认完整帧已到达。 |
| AHTT-PROTO-003 | 接收端必须校验帧头、版本、设备号、声明长度、CRC和命令。 |
| AHTT-PROTO-004 | CRC16-MODBUS必须覆盖帧头至参数末尾，不包含CRC字段本身。 |
| AHTT-PROTO-005 | 所有未特别说明的多字节数值必须按低字节在前解析和组包。 |
| AHTT-PROTO-006 | 发送端不得直接以主机结构体内存布局发送可变参数或多字节业务结构。 |
| AHTT-PROTO-007 | 首期仅接受版本`0x01`；其他版本必须丢弃，不得进入业务解析。 |

## 10. 主状态机设计

### 10.1 固定四态

```text
Init
  │ 初始化完成
  ▼
Offline
  │ 清理协议状态并准备连接
  ▼
Login
  │ TCP连接成功，触发0x01签到
  ▼
Normal
  │ 签到成功后运行周期和业务命令
  └──────── 链路断开、签到/心跳最终失败 ────────► Offline
```

### 10.2 状态转换表

| 当前状态 | 条件或事件 | 动作 | 下一状态 | 失败处理 |
|---|---|---|---|---|
| Init | 首次主函数执行 | 初始化状态字段 | Offline | 非法状态回到Init |
| Offline | 进入状态 | 清登录、收发控制、计时、帧队列和临时业务状态 | Login | 保持平台离线标志 |
| Login | TCP未连接 | 等待网络管理建立连接 | Login | 不发送签到 |
| Login | TCP连接成功 | 使能`0x01`签到发送 | Normal | 签到结果由Normal内登录标志约束在线业务 |
| Normal | `0x01`签到成功 | 设置登录成功，启动心跳、状态、校时和离线订单检查 | Normal | 未签到成功不得运行在线周期业务 |
| Normal | TCP断开 | 调用`IotAHTT_OfflineHandle` | Offline | 清理未完成收发等待状态 |
| Normal | `0x81`连续3次无应答 | 断开链路并重新进入登录流程 | Offline | 按协议重新签到 |
| Normal | 签到最终失败 | 按已确认退避策略重签或重启 | Offline或系统重启 | 20/25分钟上限待决策 |

### 10.3 状态机约束

- AHTT不得新增与四态并行的主状态机。
- 签到连续三次尝试、休眠级别和重启等待应使用四态内部标志、计数器和时间戳表达。
- `Normal`不等于已经签到成功；在线周期业务必须受`loginSucc`控制。
- `0xD1`升级状态由 UCM 管理，AHTT只记录命令处理结果，不复制 UCM 状态机。
- 状态处理不得阻塞20ms平台任务；等待动作必须使用时间戳和周期检查。

## 11. 发送架构

### 11.1 发送控制表

`c_stIotAHTTSendctrlTable`按首期23项定义，每项至少包含：

- 命令字；
- 请求或应答方向；
- 周期或立即发送属性；
- 组包函数；
- 关联命令；
- 日志开关与命令含义。

每端口的运行期发送状态继续使用公共 `CommonSendCtrl_Struct`，由`IotAHTT_GetSendCtrl()`返回指定端口、命令对应的槽位。

### 11.2 发送流程

```text
M层周期/事件/下行解析结果
  → Common_SetSendEnable
  → IotAHTT_UpCtrlSendDeal轮询控制表
  → 确定设备流水号或回传的平台流水号
  → 命令组包函数填写参数
  → IotAHTT_PackHead填写固定头并计算CRC
  → FrameQueue_PushTx
  → 设置发送标志、时间戳和应答等待计时器
```

组包函数返回参数长度；参数长度0是合法值，必须继续封装并发送零参数帧。`0xFFFF`固定表示组包失败，发送调度不得沿用GN的`dataLen > 0`判断。该差异用于支持`0x95`等零参数上行请求。

### 11.3 流水号规则

| 要求编号 | 架构要求 |
|---|---|
| AHTT-SEQ-001 | 设备主动发起的新上行请求必须使用设备侧流水号。 |
| AHTT-SEQ-002 | 设备侧流水号有效范围必须为1～60000，达到60000后回绕到1，不得发送0。 |
| AHTT-SEQ-003 | 对平台下行请求的应答必须回传该请求的流水号，不得消耗新的设备侧流水号。 |
| AHTT-SEQ-004 | 平台对设备主动请求的应答必须使用命令、有效等待状态和参数合法性共同匹配；不得将平台流水号与设备请求流水号比较。设备对平台下行请求的应答必须回传平台流水号。 |
| AHTT-SEQ-005 | FrameQueue入队失败时不得推进流水号和协议完成状态。 |

## 12. 接收架构

### 12.1 TCP流式解帧

`IotAHTT_UpCtrlRecvDeal()`通过`FrameQueue_ProcessRxData()`调用AHTT解码回调。M1严格沿用GN的消费字节反馈方式，不增加AHTT私有重组缓存。当前`FrameQueue_ProcessRxData()`在回调返回`dealLen == 0`后仍会移除整个TCP接收块，因此跨FrameQueue接收块的半包可能丢失；这是DEC-015确认的M1限制。

接收处理顺序：

```text
取得当前TCP字节流
  → 从当前位置搜索0xEA
  → 不足12字节：当前块不解析，不保证跨块保留
  → 读取声明长度
  → 声明长度非法：丢弃当前0xEA并继续搜索
  → 完整帧未到达：按GN当前搜索和消费规则结束本次处理
  → 校验版本、设备号和CRC
  → 查找接收控制项
  → 校验命令固定/可变参数长度
  → 解析字段范围、枚举、端口和单号
  → 执行业务仲裁或完成应答匹配
  → 继续处理同一缓冲区中的下一帧
```

### 12.2 异常帧恢复

| 场景 | 处理 |
|---|---|
| 帧头前存在杂字节 | 消费杂字节，保留可能的`0xEA`起点 |
| 固定头不完整 | 当前块不解析；跨FrameQueue块恢复不属于M1保证范围 |
| 声明长度小于协议最小值 | 丢弃当前候选帧头1字节并继续搜索 |
| 声明长度超过接收上限 | 丢弃当前候选帧头1字节并记录限频错误 |
| 完整帧未到达 | 按GN模式处理；不增加AHTT私有缓存 |
| 错版本、错设备号或错CRC | 丢弃当前错误帧或推进到下一候选帧头，不进入业务层 |
| 未知命令 | 消费完整帧，限频记录，不执行旧协议兼容动作 |
| 参数长度或范围非法 | 不执行业务动作；按该命令协议定义决定失败应答 |
| 错误帧后跟正常帧 | 必须能够重新同步并解析正常帧 |

### 12.3 校验边界

平台和网络输入必须检查；模块内部可信对象是否检查严格与 GN 同职责位置保持一致。

- 必须检查：长度、帧头、版本、设备号、CRC、命令、端口、枚举、范围、单号、可变数组和业务前置状态。
- `pIotAHTTCtx`只在内存分配、资源创建和链路参数等生命周期边界按 GN 位置检查。
- GN普通状态机、收发和周期路径未检查的内部上下文，AHTT对应位置不得无理由增加分支。
- 没有 GN 对应位置的新检查，代码方案必须说明实际可达失败来源和未检查后果。

## 13. 命令关联、幂等和重试

### 13.1 应答关联

AHTT部分请求与应答使用相同命令字。控制表必须通过以下信息区分：

- 当前条目是设备主动请求、平台下行请求、设备应答还是平台应答；
- 期望命令字；
- 当前端口或设备级控制槽位；
- 接收等待是否处于使能状态。

设备主动请求的应答以“有效等待项、同命令、参数合法”关联；平台应答流水号由平台独立维护，不能与设备请求流水号比较。平台下行请求由设备保存其流水号，并在对应应答中原样回送。

不存在有效等待项的迟到应答或重复应答不得重复推进业务状态。协议没有额外关联字段时，仍处于同命令有效等待期的迟到应答无法与当前应答区分。

### 13.2 单号幂等

- 协议重要业务的16位单号范围为1～10000。
- 相同单号必须视为同一次业务，不得重复启动、重复停止、重复扣费或重复创建订单。
- 对重复下行命令，应返回与首次处理一致的结果，或按协议明确的重复语义处理。
- 幂等键至少包含命令业务类型、单号和端口；是否还需包含平台流水号由单命令设计确定。
- 缓存深度、掉电保持和淘汰策略尚未确认，M4实现前必须形成独立决策。

### 13.3 超时和重试

| 类别 | 当前基线 | 最终失败动作 |
|---|---|---|
| `0x81`心跳 | 默认5分钟；等待10秒，最多重试3次 | 断开并重新签到 |
| `0x01`签到 | 连续尝试和阶梯休眠见V3.12第4.1/4.6节 | 20/25分钟重启阈值待决策 |
| 启动/停止类 | 以命令矩阵中5/10/15秒平台重发语义为准 | 必须按单命令定义，不设全局默认 |
| 状态、订单、告警 | 常见10秒×3仅作为命令级事实使用 | 不得统一推导删除订单或忽略告警 |

不得使用一个全局重试常量覆盖所有命令。每个接收控制项必须显式定义超时、最大次数和最终失败动作。

## 14. AHTT上下文和控制表容量

### 14.1 上下文概念结构

`IotAHTTCtx_Struct`应包含以下类别，不要求在第一轮一次性加入全部业务字段：

| 类别 | 字段示例 | 生命周期 |
|---|---|---|
| 状态机 | `eWorkState`、`loginSucc` | 模块生命周期 |

### 14.2 控制表容量

```text
IOT_AHTT_CMD_SEND_COUNT = 23

stSendCtrl[SYSCFG_CFG_GUN_NUM][IOT_AHTT_CMD_SEND_COUNT]
```

### 14.3 RAM预算

当前阶段采用公式预算，不在字段设计完成前编造最终字节数：

| 项目 | 预算方式 | 当前状态 |
|---|---|---|
| AHTT上下文 | `sizeof(IotAHTTCtx_Struct)`，实现后通过编译期或调试输出确认 | `[TBC]` |
| 发送运行控制 | `SYSCFG_CFG_GUN_NUM × 23 × sizeof(CommonSendCtrl_Struct)` | 可计算，待实现类型确认 |
| 接收运行控制 | `SYSCFG_CFG_GUN_NUM × 23 × sizeof(CommonRecvCtrl_Struct)` | 可计算，待实现类型确认 |
| 发送临时缓冲 | 单个可复用栈缓冲，大小不小于首期最大完整帧 | 最大帧长待计算 |
| 接收缓冲 | 复用FrameQueue TCP RX，不增加AHTT私有重组缓存 | 架构已确定；跨块半包为已知限制 |
| 平台私有参数 | 必须放入现有1280字节`MSNvmPlatPrivateParam_Union`容量内 | 字段布局待设计 |

## 16. 参数与NVM架构

### 16.1 数据归属

- 平台IP、端口、设备编号等已有公共平台参数继续使用`MSNvmPlatParam_Struct`。
- AHTT私有参数应定义`MSNvmAHTTParam_Struct`并加入`MSNvmPlatPrivateParam_Union`。
- AHTT私有参数结构总大小不得超过现有`MSNVM_PLAT_PRIVATE_PARAM_LEN`的1280字节容量。
- AHTT订单应定义`MSNvmAHTTOrderInfo_Struct`并加入`MSNvmPlatOrderInfo_Union`；结构初版按AHTT核心充电闭环所需字段建立，不复用`MSNvmGNOrderInfo_Struct`。
- 订单继续使用当前订单块，不在AHTT协议上下文中建立第二份持久化订单库；保存时`protocolType`必须为`eAswPlatType_AHTT`，`orderLen`必须为`sizeof(MSNvmAHTTOrderInfo_Struct)`。
- `IotAHTT_PackChargeRecord()`负责把当前充电数据写入`stAHTTOrderInfo`，`IotAHTT_TransformChargeRecord()`负责将掉电订单恢复为`0x94`上报数据。
- `MSNvmAHTTOrderInfo_Struct`必须覆盖订单单号、端口、启动来源、卡号、开始/结束时间、电量、剩余金额、电费、服务费、停止原因、资费关联信息及离线补报所需状态；最终字段以M4命令设计为准。

### 16.2 候选私有参数

| 参数 | 来源命令 | 是否持久化 |
|---|---|---|
| 心跳周期 | `0x02/0x03` | 持久化，并由AHTT默认初始化函数设置协议默认值 |
| 域名与端口 | `0x04` | 公共平台参数；事务更新和回滚策略待设计 |
| 最大充电时长 | `0x0A/0x0B` | 持久化，并设置协议默认值 |
| 设备工作参数 | `0x84/0x85` | `0x84`下发的运维参数全部保存；字段布局按AHTT专节核对后冻结 |
| 温度阈值 | `0xC4/0xC5` | 持久化，并设置协议默认值 |
| 二维码内容或生成参数 | 非协议功能 | `[TBD]`，建议由配置/产品层持有 |

### 16.3 持久化约束

- 只有字段合法且值发生变化时才允许请求写入。
- 多字段设置命令必须先完成全部校验，再原子更新RAM镜像并请求持久化。
- 写入失败必须保留可观察错误，不得应答成功。
- 必须检查旧固件升级后的默认值、结构大小和兼容策略。
- 每分钟订单保存策略必须评估NVM写放大、掉电一致性和寿命，不得由协议层直接循环写入。
- `IotAHTT_SetPrivateParam()`必须设置心跳周期、最大充电时长、`0x84`运维参数、温度阈值及其他AHTT私有参数的默认值；初版字段命名和分组可以参考GN，但值、单位和范围只能来自AHTT事实台账。

## 17. 充电、订单、刷卡和告警边界

### 17.1 核心充电闭环

```text
0x4D平台启动
  → Recv校验长度、单号、端口、模式和费率
  → M层检查插枪、空闲、安全和故障状态
  → 转换为当前计费模型和启动接口
  → 发送0x4D结果
  → 充电中周期发送0x93
  → 0x4B平台停止或本地停止
  → 本地完成停止与订单落盘
  → 发送0x4B结果和0x94结束事件
  → 平台确认后推进订单上报状态
```

- 订单业务状态必须与协议上报状态分离。
- 平台未应答不得删除本地订单。
- 重复`0x4D/0x4B`必须先经过单号幂等检查。
- 停止原因必须集中映射当前错误/监控枚举到AHTT协议值。

### 17.2 刷卡

- `0x4C`只负责协议鉴权和费率接收；物理卡读取由现有卡模块负责。
- AHTT卡描述符必须使用`eCddCardType_UUID`，`AswMonitor`向`IotAHTT_SwipCardCharge()`传入物理UUID。
- `0x4C`线上5字节卡号沿用旧AHTT格式：直接复制当前卡驱动保存的物理UUID前4字节，不额外反转，再追加`0x00`作为第5字节。
- 卡号比较和订单保存必须使用同一份5字节规范化AHTT卡号，禁止一处使用16字节`authCardID`、另一处使用5字节线上卡号直接比较。
- 首卡锁定、同卡累计、异卡拒绝、拔枪清理和鉴权失败动作由独立业务状态定义。
- 未鉴权先充电的历史策略默认不继承，除非用户另行确认并完成安全评审。
- 日志不得输出完整卡号。

### 17.3 告警

- `0xC1～0xC3`按故障出现和恢复变位触发，不得在状态未变化时无限重复发送。
- 平台不应答时按命令级超时策略重发。
- 超温等本地保护动作由当前安全模块执行；AHTT只上报结果，不能作为唯一保护路径。
- `0xC4/0xC5`只配置和查询阈值，不直接实现温度采样和保护控制。

### 17.4 `0x81`心跳状态

`0x81`参数固定为5字节：

| 字段 | 长度 | 当前实现来源 |
|---|---:|---|
| 信号制式 | 1 | 当前4G模组填`0x02`；`0x01`表示2G |
| 信号强度 | 1 | `CddNetM_GetCsq()`的低8位，实际合法范围需用模组与平台联调确认 |
| 12通道状态 | 3 | 每通道2bit，低位通道在前 |

状态值固定为：`00`空闲、`01`工作、`10`故障、`11`离线。通道索引`ch`从0开始时：

```text
byteIndex = ch / 4
bitPos    = (ch % 4) * 2
```

状态数组必须先初始化为`FF FF FF`，使所有未配置通道默认为离线，再使用掩码覆盖`0 ～ SYSCFG_CFG_GUN_NUM-1`的实际状态。旧参考项目`AHTT_dev_getGunState()`的索引和移位方式可以复用，但其全零初始化会把未配置通道表示为空闲，当前实现不得照搬。

## 18. `0xD1` OTA架构

### 18.1 固定调用边界

```text
平台0xD1
  → IotAHTT_RecvSetUpdate
  → 校验固定长度、升级内容、MD5和当前业务状态
  → 参考IotGN_RecvSetUpdate组装CddNetMSocketPara_Union
  → 选择UCM通道、执行模式和超时
  → SSUcm_ReqStartOTA
  → UCM负责下载、分区写入、升级条件、失败处理和重启
  → IotAHTT_SendUpdateRsp返回协议结果
```

### 18.2 架构要求

| 要求编号 | 架构要求 |
|---|---|
| AHTT-OTA-001 | AHTT必须通过`SSUcm_ReqStartOTA()`启动升级，不得直接擦写升级分区。 |
| AHTT-OTA-002 | 升级前必须使用当前`SSUcm_CheckUpdateCondition()`及业务安全条件，平台命令不得绕过充电状态检查。 |
| AHTT-OTA-003 | 旧项目固定服务器账号、口令、目录和板型字符串不得复制到AHTT源码或文档。 |
| AHTT-OTA-004 | `0xD1`参数非法或AHTT本地前置条件不满足时必须返回失败；参数校验通过并调用`SSUcm_ReqStartOTA()`后必须按DEC-007应答成功，不检查UCM是否实际受理。 |
| AHTT-OTA-005 | AHTT日志不得输出升级凭据或敏感下载参数。 |
| AHTT-OTA-006 | `0xD1`提供的MD5与UCM现有完整性机制如何衔接必须在代码实现前关闭。 |

### 18.3 与GN不同的阻断点

GN升级命令能够在解析函数内构造UCM下载参数并选择FTP及立即/空闲执行模式；AHTT V3.12当前提取到的`0xD1`仅提供8字节升级内容和16字节MD5，不能从现有事实唯一推导完整下载地址和执行策略。UCM接口保持`void`，AHTT不等待也不读取受理结果。

因此，以下内容必须由平台抓包、现网配置或用户决策补齐后才能实现`0xD1`业务：

- 8字节升级内容的编码和业务含义；
- 下载服务器、端口、路径和凭据来源；
- FTP或HTTP通道选择；
- 立即升级或空闲升级；
- 超时时间；
- MD5校验的执行模块和失败结果；
- 升级请求已受理与下载完成之间的应答语义。

## 19. 二维码架构

- 当前单端口二维码按设备编号生成，是否包含枪号由产品/平台规则决定。
- 二维码字符串由配置或产品层生成并持久化，协议模块只读取规范化结果。
- 显示模块负责渲染和刷新，AHTT不得直接操作显示缓冲。
- 域名、设备编号或其他参数变化后是否立即刷新以及掉电恢复策略必须在二维码功能设计中定义。
- 源码、日志和文档不得包含测试环境账号、口令或固定测试桩号。

## 20. 实时性、任务和并发

当前`AswPlatM_MainFunction()`运行在`Task_20msB`中，与`CddNetM_MainFunction()`、`SSUcm_MainFunction()`和`MSNvm_MainFunction()`共享20ms周期任务。

| 要求编号 | 架构要求 |
|---|---|
| AHTT-TIME-001 | AHTT主函数不得使用阻塞等待、长轮询或同步下载。 |
| AHTT-TIME-002 | 签到退避、心跳、重试和周期上报必须使用时间戳驱动。 |
| AHTT-TIME-003 | 单次主函数执行必须有界；大量粘包不得导致20ms任务长期独占。 |
| AHTT-TIME-004 | OTA下载和Flash处理必须由UCM主函数推进，不得在AHTT解析回调中执行长耗时操作。 |
| AHTT-TIME-005 | 当前阶段沿用`MSNvm_WriteParaBlock()`同步写入和`portMAX_DELAY`互斥等待机制，不新增异步接口；必须通过实测记录其对20ms任务的最大阻塞时间。 |
| AHTT-TIME-006 | M1必须测量最坏收发处理时间、任务栈余量和看门狗风险。 |

AHTT不新增ISR接口。网络、NVM、UCM和充电业务共享数据继续遵循各模块现有任务上下文和接口契约。

## 21. 日志与可观测性

必须记录并可限频输出：

- 主状态转换和离线原因；
- 命令、方向、流水号、单号、端口和处理结果；
- 长度、版本、设备号、CRC和参数校验失败类别；
- 应答超时次数、重试上限和最终失败动作；
- 参数持久化请求和失败；
- OTA请求是否被接受、UCM状态和失败原因；
- 订单补报状态和平台确认。

不得记录：

- 完整卡号；
- 平台、FTP或HTTP账号和口令；
- 密钥、令牌和完整敏感下载地址；
- 不必要的完整SIM卡号。

日志失败不得改变充电保护、协议状态或OTA安全行为。
